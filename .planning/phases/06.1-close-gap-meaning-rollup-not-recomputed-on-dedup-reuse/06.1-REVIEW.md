# Phase 06.1: Code Review Report

**Reviewed:** 2026-09-17T00:00:00Z
**Depth:** standard
**Files Reviewed:** 4
**Status:** issues_found

## Summary

The phase's actual deliverable is a small, well-targeted change to
`linkMeaningToWordForm`: the new-pair insert now runs inside a
`db.transaction('rw', [wordFormMeanings, meanings], ...)` block that also calls
`aggregateMeaningFromPairs(meaningId)`, so a newly-created junction row
immediately rolls up into the parent `Meaning`'s `isActive` /
`firstUseDate` / `lastUseDate`. The two new test files exercise this
correctly: they cover the "new pair triggers re-aggregation" case, the
"existing pair skips re-aggregation" (D-02) guard, and the specific audit-gap
scenario (dedup reuse of a previously-inactive meaning onto a new word form
refreshes `isActive`/`lastUseDate`). I traced the logic against
`aggregateMeaningFromPairs` in `meaning.service.ts` and the calling code in
`wordEntry.service.ts`, and the new behavior is correct for the scenarios it
was written to cover.

`.gitignore` is confirmed to be a trivial, unrelated one-line addition
(`.gsd/`) from a concurrent commit — no issues there.

Two real gaps remain, both centered on the fact that the "keep the Meaning
rollup in sync" invariant this phase establishes is applied inconsistently
across the file, and the idempotency check that gates the new transaction is
not itself part of that transaction.

## Warnings

### WR-01: `unlinkMeaning` does not re-aggregate the parent Meaning, breaking the sync invariant this phase establishes

**File:** `src/db/services/wordFormMeaning.service.ts:64-72`
**Issue:** `linkMeaningToWordForm` (new-pair path) and `updatePairFields` both
call `aggregateMeaningFromPairs` after mutating a junction row, specifically
so the parent `Meaning`'s `isActive`/`firstUseDate`/`lastUseDate` never go
stale relative to its pairs. `unlinkMeaning` deletes a junction row but never
calls `aggregateMeaningFromPairs`:
```ts
export async function unlinkMeaning(
  wordFormId: number,
  meaningId: number
): Promise<void> {
  await db.wordFormMeanings
    .where('[wordFormId+meaningId]')
    .equals([wordFormId, meaningId])
    .delete()
}
```
If this deletes the last active pair for a meaning, the meaning is left with
a stale `isActive: true` and a stale `lastUseDate` forever — the same class
of bug this phase was opened to close, just on the delete path instead of the
create path. It also means `aggregateMeaningFromPairs`'s "if no pairs exist,
leaves the meaning unchanged" edge case (`meaning.service.ts:20`) is silently
relied upon here without ever running, so a meaning that ends up with zero
pairs keeps arbitrary leftover data instead of being flagged inactive.
`unlinkMeaning` is not currently wired to any UI action (only referenced by a
"still exported" backward-compat test), so there is no live user-facing
impact today — but it is a live foot-gun the moment someone wires a "remove
pair" button to it.
**Fix:** Wrap the delete in the same transaction + re-aggregate pattern used
elsewhere:
```ts
export async function unlinkMeaning(
  wordFormId: number,
  meaningId: number
): Promise<void> {
  await db.transaction('rw', [db.wordFormMeanings, db.meanings], async () => {
    await db.wordFormMeanings
      .where('[wordFormId+meaningId]')
      .equals([wordFormId, meaningId])
      .delete()
    await aggregateMeaningFromPairs(meaningId)
  })
}
```
Also worth deciding explicitly what `aggregateMeaningFromPairs` should do
when a meaning ends up with zero pairs (currently: nothing), since that's the
exact case `unlinkMeaning` will trigger for a meaning's last pair.

### WR-02: Idempotency check runs outside the atomic transaction — TOCTOU race can still create duplicate junction rows

**File:** `src/db/services/wordFormMeaning.service.ts:25-46`
**Issue:** The "does this pair already exist" read (lines 25-28) happens
*before* the new `db.transaction(...)` block (lines 37-46) that performs the
insert + aggregate. Between that read and the transaction being opened there
is no lock: two concurrent calls to `linkMeaningToWordForm(wordFormId,
meaningId)` for the same pair (e.g. a rapid double-submit, or two calls
running in independent `Promise.all` branches rather than nested inside one
`addWordEntry` transaction) can both observe "no existing pair" before either
commits its insert, and both proceed to insert. The compound index used for
the lookup, `[wordFormId+meaningId]` (`src/db/db.ts:16,23,31`), is a plain
index, not a unique one (Dexie unique indexes are prefixed with `&`), so
nothing at the schema level prevents the duplicate row either. The result is
two junction rows for the same `(wordFormId, meaningId)` pair —
`getPairsWithDetails()` would then surface the same logical pair twice to the
UI, and `aggregateMeaningFromPairs` would count the same underlying
observation twice when computing rollups. This is a pre-existing gap in the
idempotency check (not introduced by this phase's diff), but it directly
undermines the "pair + meaning stay in sync" guarantee this phase is meant to
harden, so it's in scope for this review.
**Fix:** Either move the existence check inside the same transaction (so the
check and the insert commit atomically under Dexie's transaction locking), or
add a unique compound index (`&[wordFormId+meaningId]`) in a new schema
version and treat the resulting `ConstraintError` on `add()` as the
"idempotent no-op" signal instead of relying on a pre-check.

## Info

### IN-01: No test covers transaction atomicity/rollback for the new insert+aggregate block

**File:** `src/db/services/wordFormMeaning.service.test.ts`
**Issue:** The new `db.transaction(...)` wrapper's main value is that the
insert and the aggregate either both happen or neither does. None of the new
tests exercise a failure inside the transaction (e.g. `aggregateMeaningFromPairs`
throwing) to confirm the junction-row insert is rolled back rather than left
orphaned without a corresponding rollup.
**Fix:** Add a test that stubs/forces `aggregateMeaningFromPairs` (or the
`db.meanings.update` call it makes) to throw, and asserts the junction row
from the same `linkMeaningToWordForm` call was not persisted afterward.

### IN-02: No regression test for the TOCTOU race described in WR-02

**File:** `src/db/services/wordFormMeaning.service.test.ts`
**Issue:** All idempotency tests call `linkMeaningToWordForm` sequentially
(`await`ed one after another), which cannot exercise the interleaving
described in WR-02. There is no `Promise.all([linkMeaningToWordForm(...),
linkMeaningToWordForm(...)])` test to pin down current (possibly buggy)
concurrent behavior.
**Fix:** Add a concurrency test once WR-02 is fixed, asserting exactly one
junction row exists after two concurrent calls for the same pair.
