### Code Review Findings (Plan 01)

**WR-01 (Warning):** Edge case gap — missing/non-array childProfile not covered by specific error message. The check guards on `Array.isArray(...)` before checking length, so a hand-edited backup missing the key entirely, with `childProfile: null`, or `childProfile: {...}` (object instead of array) will show generic "corrupt" message instead of the specific "no child profile data" message. No regression test for this case. Reviewer suggested widening the guard.

**WR-02 (Warning):** Stale decision ID in comment at line 172 — cites D-01 (which is the validateBackupData check) instead of D-02 (which is the importData throw). Per phase 06.3's own mandate on traceability, this is ironic.

**WR-03 (Warning):** Duplicated childProfile.length===1 invariant — implemented independently at validateBackupData line 84 and importData lines 196-204 with no shared source of truth. Future changes to the invariant require updating both places (and DataSection.tsx's error-discrimination string, see WR-04).

**WR-04 (Warning):** Error-code discrimination via magic strings and `.includes()` instead of shared constants. The three error codes ('wrong-schema-version', 'invalid-child-profile-count', 'corrupt') are duplicated between dataManagement.ts (thrown) and DataSection.tsx (matched), with no compile-time link. A typo or rename in one file won't fail to compile — it will silently fall through to the generic branch.

**WR-05 (Warning, pre-existing):** CSV export has no formula-injection guard — `escapeCSVCell` does not neutralize leading `=`, `+`, `-`, `@` characters. Values from untrusted imported backups could round-trip through import → CSV export → open in Excel/Sheets and execute as formulas.

**IN-01 (Info):** Key name `importErrorDescriptionMissingProfile` only describes half the failure mode (missing, not "2+ profiles"). Consider `importErrorDescriptionInvalidProfileCount` in follow-up.

### Verdict on Plan 01

**Status:** BLOCKED on missing-key edge case, but data-loss risk is zero (per reviewer).

The core goal (prevent data loss from empty/multi-profile array cases) is 100% achieved. The code correctly rejects both the empty-array and 2-entry cases with a distinct error before any write occurs. However, the implementation has a coverage gap: a backup with a missing or malformed childProfile key falls through to the generic "corrupt" message instead of the specific "no child profile data" message. This is flagged as WR-01 in the code review and is out of scope for the current phase per the CONTEXT.md decisions, which explicitly cover D-01/D-02 for the array-length axis but do not mention the missing-key scenario.

The PLAN.md's must-have text says "childProfile.length !== 1" which technically requires childProfile to be an array. The plan did not explicitly require handling the missing-key case in the specific error. However, the i18n message itself says "has no child profile data, or has more than one," which suggests the intent covers that case.

**Recommendation:** Accept the current implementation for v1 (data-loss risk is zero). Route WR-01 to a follow-up import-hardening phase per D-06 alongside the other deferred import-validation warnings (CSV injection, category validation, referential integrity, round-trip test).
