# Phase 06.3: Address tech debt: REQUIREMENTS.md traceability, import validation footgun, verification artifact hygiene - Context

**Gathered:** 2026-09-17
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase closes the tech-debt items identified in the v1.0 milestone audit (`.planning/v1.0-MILESTONE-AUDIT.md`, audited 2026-09-17, status: `tech_debt`). Three items, no code/functional gaps:

1. **Import validation footgun** — `validateBackupData` in `src/features/settings/services/dataManagement.ts` accepts a backup with an empty `childProfile` array (`Array.every()` is vacuously true on `[]`). Importing such a file wipes existing data via `db.transaction` clear+bulkAdd, leaves 0 profile rows, and `AuthGuard` redirects to onboarding — a data-loss/lockout footgun on restore.
2. **REQUIREMENTS.md traceability + hygiene** — the Traceability table stops at PWA-03 (Phase 5); PREREL-01..05 (Phase 6) are defined in ROADMAP.md and fully verified in `06-VERIFICATION.md` but were never added. Separately, 14 of 26 v1 requirements have `SUMMARY.md` frontmatter `requirements-completed` left empty despite being verified in the corresponding phase `VERIFICATION.md`.
3. **Verification artifact hygiene** — `05-VERIFICATION.md` and `06-VERIFICATION.md` both have frontmatter `status: passed` but body text `**Status:** human_needed` — internally inconsistent status field.

Out of scope for this phase (explicitly deferred during discussion, not new capabilities): the other three import-validation warnings from `06.2-REVIEW.md` (CSV formula-injection guard, category validation on import, referential integrity between imported `wordForms`/`meanings`/`wordFormMeanings`, missing `wordForms` round-trip test), and any tooling/lint to prevent future frontmatter/body status drift in `VERIFICATION.md` generation.

</domain>

<decisions>
## Implementation Decisions

### Import validation footgun
- **D-01:** `validateBackupData` must require `childProfile.length === 1` (not just `>= 1`). Rationale: MULTI-01 (multiple child profiles) is explicitly out of scope for v1 (see REQUIREMENTS.md "Out of Scope"), so a valid v1 backup always represents exactly one child.
- **D-02:** On failing this new check, throw a new distinct error (not the generic `'corrupt'` used today) with its own i18n message explaining the backup has no/invalid child profile data — mirrors the existing pattern where `'wrong-schema-version'` is already distinguished from `'corrupt'` in `importData` (dataManagement.ts:170-195).
- **D-03:** New i18n key (e.g. `errors.importMissingProfile` or similar, exact key left to planner/executor) added alongside the existing `importErrorDescriptionVersion` / corrupt-file keys in both `en` and `pl` locale files, with plain wording: "This backup file has no child profile data and cannot be imported."
- **D-04:** Add an explicit regression test asserting `validateBackupData` rejects a backup with an empty `childProfile` array (and, given D-01, also one with 2+ profiles) — this was an audit-flagged bug, worth a dedicated test rather than relying on incidental coverage.
- **D-05:** Scope stays limited to the `childProfile` count check. Do NOT extend this same strictness to `wordForms`/`meanings`/`wordFormMeanings` — those arrays are legitimately empty for a freshly onboarded child with zero entries; broadening the check there would reject valid backups. — **Reversibility:** reversible — purely a validation-logic scope choice, easy to widen later if needed.
- **D-06 (deferred, not in scope):** The other three import-related warnings from `06.2-REVIEW.md` (CSV formula-injection guard, category validation, referential integrity between imported `wordForms`/`meanings`/`wordFormMeanings`, missing `wordForms` round-trip test) are NOT bundled into 06.3. They are separate, non-trivial pieces of work better suited to their own follow-up phase.

### REQUIREMENTS.md traceability + hygiene scope
- **D-07:** Both parts of the cross-phase doc gap are in scope: (a) add PREREL-01..05 rows to the REQUIREMENTS.md Traceability table pointing at Phase 6, and (b) backfill the `requirements-completed` frontmatter field in the 14 affected `SUMMARY.md` files (FOUND-01..04, ONBD-01, BROWSE-01..04, REPORT-02, DATA-01, DATA-03, PWA-01, PWA-03 — see audit table in `v1.0-MILESTONE-AUDIT.md` §2 for the exact phase/plan mapping of each).
- **D-08:** Add PREREL-01..05 as rows only in the existing Traceability table (`Requirement | Phase | Status`) — do NOT add a full "### Pre-release Polish" prose section under "v1 Requirements" mirroring Foundation/Onboarding. The full requirement definitions already live in ROADMAP.md's Phase 6 section; duplicating them in REQUIREMENTS.md would create a second source of truth to keep in sync.
- **D-09:** Update the "Coverage" summary at the bottom of REQUIREMENTS.md's Traceability section (currently "v1 requirements: 26 total... Unmapped: 0") to reflect the +5 PREREL rows once added.

### Verification artifact hygiene
- **D-10:** Canonical status stays `passed` in both files. Fix the body text in `05-VERIFICATION.md` and `06-VERIFICATION.md` from `**Status:** human_needed` to `**Status:** passed`, keeping the existing `human_verification` checklist below it unchanged (it documents legitimate device/browser-only checks, not code gaps — frontmatter `status: passed` and `score` fields already reflect this correctly).
- **D-11:** Do NOT introduce a new status vocabulary value (e.g. `passed_human_needed`) — scope stays to fixing the two existing inconsistent files, not changing the status taxonomy.
- **D-12 (deferred, not in scope):** No tooling/lint change to prevent recurrence of this frontmatter/body mismatch in future `VERIFICATION.md` generation. Noted as a possible future improvement to the `gsd-verifier`/verify-phase workflow template, not part of this phase.

### Claude's Discretion
- Exact i18n key name for the new import error message (D-03) — planner/executor picks something consistent with existing `errors.*` naming.
- Whether the regression test (D-04) lives in the existing `dataManagement.test.ts` describe block for `validateBackupData` or a new one — existing file/structure should guide this.
