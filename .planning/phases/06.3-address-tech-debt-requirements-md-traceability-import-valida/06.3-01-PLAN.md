<objective>
Close the import-validation footgun identified in the v1.0 milestone audit (`.planning/v1.0-MILESTONE-AUDIT.md` §4): `validateBackupData` currently accepts a backup JSON with an empty `childProfile` array (`Array.every()` is vacuously true on `[]`), and `importData` would clear existing tables and write zero profile rows, tripping `AuthGuard`'s onboarding redirect while orphaning `wordForms`/`meanings`/`wordFormMeanings` in IndexedDB — a data-loss/lockout footgun on restore.

Purpose: A parent restoring a backup on a new device (or after clearing browser storage) must never silently lose their child's record to a malformed or hand-edited backup file. Since MULTI-01 (multiple child profiles) is out of scope for v1, a valid backup always has exactly one `childProfile` row (D-01).

Output: `validateBackupData` rejects any `childProfile` array whose length is not exactly 1; `importData` surfaces this as a distinct, non-generic error (`invalid-child-profile-count`) with its own parent-facing i18n message in both locales, verified before any table is cleared.
