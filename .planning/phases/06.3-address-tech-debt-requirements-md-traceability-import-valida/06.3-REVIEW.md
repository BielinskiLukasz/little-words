# Phase 06.3: Code Review Report

**Reviewed:** 2026-09-18T00:00:00Z
**Depth:** standard
**Files Reviewed:** 5
**Status:** issues_found

## Summary

Reviewed the plan 06.3-01 change that rejects backup imports whose `childProfile` array isn't exactly length 1 (closing the "empty/multi-profile backup wipes data" footgun), the new `invalid-child-profile-count` error path, its i18n strings, and the regression tests. The core fix is correctly wired: `validateBackupData`'s new length check sits after the `every(isValidChildProfile)` guard so it actually fires on the empty-array vacuous-truth case, and the `importData`-level check runs strictly before `db.transaction`, so a rejected import performs zero writes in every tested scenario (0 profiles, 2 profiles). Tests for those two cases exist at both layers.

However, the new "distinct message" behavior has a real coverage gap: it only fires when `childProfile` is present *and* is an array of the wrong length. A backup where the `childProfile` key is missing entirely, `null`, or not an array at all — which the shipped copy explicitly claims to handle ("has no child profile data") — silently falls through to the generic `corrupt` message instead. There's also a traceability slip (an inline comment cites the wrong decision ID, ironic given this phase's own subject matter), duplicated business-rule logic across two functions with no shared source of truth, and a fragile string-matching pattern in the UI layer for error discrimination. One pre-existing, in-scope-file security nit (CSV formula injection) is also noted for completeness.

## Warnings

### WR-01: "no child profile data" error message doesn't fire when childProfile is missing/non-array

**File:** `src/features/settings/services/dataManagement.ts:196-204`
**Issue:** The new specific-error check only throws `invalid-child-profile-count` when `childProfile` is present **and** `Array.isArray(...)` is true **and** its length isn't 1:
```ts
if (
  typeof parsed === 'object' &&
  parsed !== null &&
  'childProfile' in parsed &&
  Array.isArray((parsed as Record<string, unknown>).childProfile) &&
  ((parsed as Record<string, unknown>).childProfile as unknown[]).length !== 1
) {
  throw new Error('invalid-child-profile-count')
}
```
If `childProfile` is entirely absent from the JSON, `null`, or e.g. an object instead of an array, this block is skipped (the `Array.isArray` guard fails), execution falls through to `validateBackupData`, which returns `false` for the same underlying reason (`!Array.isArray(d.childProfile)`) and the generic `corrupt` message is shown instead.

This directly contradicts the shipped copy, which was written to cover exactly this case:
> "This backup file has no child profile data, or has more than one, and cannot be imported." (`en/common.json` → `settings.importErrorDescriptionMissingProfile`)

A hand-edited or partially-corrupted backup missing the `childProfile` key altogether is a very plausible way to hit "no child profile data," yet the user gets "This file doesn't appear to be a Little Words backup" instead of the message that was written specifically to explain this failure mode. There is also no regression test for the missing-key case (only the empty-array and 2-entry cases are tested).
**Fix:** Widen the guard so any invalid shape of `childProfile` (missing, wrong type, or wrong length) routes to the specific message:
```ts
if (typeof parsed === 'object' && parsed !== null) {
  const cp = (parsed as Record<string, unknown>).childProfile
  if (!Array.isArray(cp) || cp.length !== 1) {
    throw new Error('invalid-child-profile-count')
  }
}
```
Add a test asserting `importData` throws `invalid-child-profile-count` (not `corrupt`) for a backup where the `childProfile` key is omitted entirely.

### WR-02: Comment cites the wrong decision ID (D-01 instead of D-02)

**File:** `src/features/settings/services/dataManagement.ts:172`
**Issue:** The doc comment above `importData` reads:
```ts
// Throws with message 'invalid-child-profile-count' if childProfile.length !== 1 (D-01).
```
Per this phase's own `06.3-CONTEXT.md`, **D-01** is "`validateBackupData` must require `childProfile.length === 1`" and **D-02** is "on failing this new check, throw a new distinct error ... in `importData`". The commit messages (`0c15a0d`, `5cf47bd`) and `06.3-01-PLAN.md`/`06.3-PATTERNS.md` consistently use D-01 for the `validateBackupData` check and D-02 for the `importData` throw. This inline comment mislabels the `importData`-side behavior as D-01, which is exactly the kind of traceability drift this phase (06.3, "requirements.md traceability") is meant to close.
**Fix:** Change the citation to `(D-02)`:
```ts
// Throws with message 'invalid-child-profile-count' if childProfile.length !== 1 (D-02).
```

### WR-03: childProfile.length===1 invariant duplicated with no shared source of truth

**File:** `src/features/settings/services/dataManagement.ts:84` and `196-204`
**Issue:** The "exactly one child profile" rule is now implemented independently in two places: `validateBackupData` (`if (d.childProfile.length !== 1) return false`) and the ad-hoc pre-check in `importData`. They currently agree, but nothing enforces that they stay in sync — a future change to the invariant (e.g. to support `MULTI-01` later) requires remembering to update both call sites, plus the string-matching consumer in `DataSection.tsx` (see WR-04). This is the same class of "hardcoded three times" bug the 06.2 audit already flagged for `schemaVersion`.
**Fix:** Extract a single helper, e.g. `isChildProfileCountValid(childProfile: unknown): childProfile is ChildProfile[]`, and call it from both `validateBackupData` and `importData`'s pre-check.

### WR-04: Error-code discrimination via `.includes()` on raw strings

**File:** `src/features/settings/components/DataSection.tsx:53-61`
**Issue:**
```ts
const message = err instanceof Error ? err.message : ''
if (message.includes('wrong-schema-version')) { ... }
else if (message.includes('invalid-child-profile-count')) { ... }
else { ... }
```
The three error "codes" (`'wrong-schema-version'`, `'invalid-child-profile-count'`, `'corrupt'`) are magic strings duplicated between `dataManagement.ts` (where they're thrown) and `DataSection.tsx` (where they're matched), with no shared constant and no compile-time link between them. `.includes()` is used instead of `===`/`message` equality, so a typo or future rename of one of the thrown strings will not fail to compile — it will silently fall through to the generic "corrupt" branch, hiding the real error class from the user with no test failure to catch it (none of the current tests assert on the DataSection-level UI branch, only on the raw thrown `Error.message`).
**Fix:** Export the three literals as a shared const/enum from `dataManagement.ts` (e.g. `export const ImportErrorCode = { WrongSchemaVersion: 'wrong-schema-version', InvalidChildProfileCount: 'invalid-child-profile-count', Corrupt: 'corrupt' } as const`) and import it in `DataSection.tsx`, matching with `===` against `err.message`.

### WR-05: CSV export has no formula-injection guard (pre-existing, in-scope file)

**File:** `src/features/settings/services/dataManagement.ts:93-98, 100-124`
**Issue:** `escapeCSVCell` only wraps a cell in quotes when it contains a comma, quote, or newline — it does not neutralize leading `=`, `+`, `-`, or `@` characters. `meaning.text` and `wordForm.form` are free-text fields that (per this very diff's own security model) can arrive from an **imported, hand-edited/untrusted backup file** and later be re-exported via `exportMeaningsCSV`. If a value such as `=1+1` or `=HYPERLINK(...)` round-trips through import → CSV export → is opened in Excel/Sheets/Numbers by the parent or, per this app's stated core value, "a specialist consultation," it can execute as a formula (CSV/formula injection, CWE-1236). This isn't part of the diff under review, but it's in the file scope for this review and is adjacent to the exact threat model (untrusted imported data) this phase is hardening.
**Fix:** Prefix cell values that start with `=`, `+`, `-`, or `@` with a leading `'` (or a space) before applying the existing comma/quote escaping, e.g.:
```ts
function escapeCSVCell(value: string): string {
  const neutralized = /^[=+\-@]/.test(value) ? `'${value}` : value
  if (neutralized.includes(',') || neutralized.includes('"') || neutralized.includes('\n') || neutralized.includes('\r')) {
    return '"' + neutralized.replace(/"/g, '""') + '"'
  }
  return neutralized
}
```
