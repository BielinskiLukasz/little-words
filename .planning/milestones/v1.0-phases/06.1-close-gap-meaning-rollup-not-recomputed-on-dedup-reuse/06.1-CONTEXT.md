# Phase 06.1: Close gap: meaning rollup not recomputed on dedup reuse - Context

**Gathered:** 2026-09-16
**Status:** Ready for planning

<domain>
## Phase Boundary

A meaning's `isActive`/`firstUseDate`/`lastUseDate` rollup must always be recomputed from its linked pairs — including when an existing (previously inactive) meaning is reused on a new word form via the add-entry autocomplete dedup path. Today, `addWordEntry`'s dedup branch calls `linkMeaningToWordForm` but nothing re-aggregates the parent `Meaning`, so the Dashboard's Active Meanings count and the Doctor Report can silently stay stale (milestone v1.0 audit, blocker 1: DASH-01/DASH-02/DASH-03/REPORT-01).

Out of scope: JSON export/import schema v3 migration (Phase 06.2, separate gap), the dead `unlinkMeaning()` code (tech debt, not this gap), and any other new capability.

</domain>

<decisions>
## Implementation Decisions

### Fix Placement

- **D-01:** Move the `aggregateMeaningFromPairs(meaningId)` call inside `linkMeaningToWordForm` itself (`src/db/services/wordFormMeaning.service.ts:15-39`), rather than adding a targeted call only in `addWordEntry`'s dedup branch. This matches the existing pattern in `updatePairFields` and `deleteWordForm`, and guarantees every current and future caller of `linkMeaningToWordForm` gets correct rollup behavior — closing off the class of bug, not just this one call site.
- **D-02:** The early-return / idempotent no-op path in `linkMeaningToWordForm` (when the `[wordFormId+meaningId]` pair already exists, lines 25-27) does **not** call `aggregateMeaningFromPairs`. Nothing changed on that pair, so there is nothing to re-aggregate — keeps the fix strictly scoped to the reported gap rather than adding a speculative defensive recompute.

### Test Coverage

- **D-03:** Add both a unit test and an integration test:
  - Unit test in `src/db/services/wordFormMeaning.service.test.ts` asserting `linkMeaningToWordForm` triggers `aggregateMeaningFromPairs` on the parent meaning when a new pair is created (following the existing `updatePairFields` test pattern in that file).
  - Integration test in `src/db/services/wordEntry.service.test.ts` reproducing the exact audit scenario: `addWordEntry` called with `existingMeaningId` pointing at a previously-inactive meaning, asserting `Meaning.isActive`/`lastUseDate` refresh correctly after the call.

### Deferred / Out of Scope

- **D-04:** `unlinkMeaning()` (`src/db/services/wordFormMeaning.service.ts:56-64`) stays untouched in this phase. It's flagged as dead code (no live caller, no re-aggregation) in the milestone audit's tech-debt list, not its blocker list — fixing/removing it here would widen the diff beyond this phase's stated goal.

### Claude's Discretion
- Exact wording/placement of the doc comment on `linkMeaningToWordForm` noting it now re-aggregates (follow the existing comment style already on `updatePairFields`).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `aggregateMeaningFromPairs(meaningId)` in `meaning.service.ts` — already implements the correct recompute logic (isActive = OR of pairs, firstUseDate = min, lastUseDate = max); no changes needed, just needs to be called from the missing site
- `updatePairFields` in `wordFormMeaning.service.ts:70-81` — exact transaction pattern to mirror: wraps `db.wordFormMeanings` + `db.meanings` in `db.transaction('rw', ...)`, updates the pair, then calls `aggregateMeaningFromPairs`

### Established Patterns
- Every other pair-mutating function (`updatePairFields`, `deleteWordForm`) re-aggregates the affected meaning(s) inside the same transaction as the pair write — `linkMeaningToWordForm` is the one exception, which is the root cause of this gap
- `addWordEntry` already runs its whole body inside `db.transaction('rw', [db.wordForms, db.meanings, db.wordFormMeanings], ...)` — adding `db.meanings` write access inside `linkMeaningToWordForm` doesn't require touching the transaction's table list at the call site, but `linkMeaningToWordForm` itself will need `db.meanings` in scope for the aggregation call

### Integration Points
- `linkMeaningToWordForm` is called from `addWordEntry` (both the new-meaning and dedup branches) — the fix applies uniformly to both, but only the dedup branch currently exhibits the bug (the new-meaning branch already sets correct values via `addMeaning`, so the added aggregate call there is a harmless recompute of the same values)

</code_context>
