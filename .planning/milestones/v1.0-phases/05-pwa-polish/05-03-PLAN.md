  </read_first>

  <action>
    Create the directory .github/workflows/ if it does not exist, then create .github/workflows/deploy.yml using the Write tool.

    The workflow file must have:

    name: Deploy to GitHub Pages

    on:
      push:
        branches: [main]

    No other triggers. No workflow_dispatch, no pull_request trigger.

    permissions:
      contents: write

    (peaceiris/actions-gh-pages@v4 requires write access to push to the gh-pages branch)

    jobs:
      deploy:
        runs-on: ubuntu-latest
        steps:
          1. actions/checkout@v4 — check out the repository
          2. actions/setup-node@v4 with node-version: '22', cache: 'npm' — install Node 22 with npm dependency caching
          3. run: npm ci — clean install from lockfile; fails fast if package-lock.json is out of sync
          4. run: npm run lint — must exit 0 or workflow fails; no continue-on-error
          5. run: npm run test — must exit 0 or workflow fails; no continue-on-error
          6. run: npm run build — produces dist/ directory
          7. peaceiris/actions-gh-pages@v4 with:
               github_token: ${{ secrets.GITHUB_TOKEN }}
               publish_dir: ./dist
               publish_branch: gh-pages
               keep_files: false

    The github_token secret is automatically provided by GitHub Actions — no manual secret setup is required.
    keep_files: false ensures stale files from previous deployments do not accumulate in the gh-pages branch.
    publish_dir: ./dist — the Vite build output directory.
    publish_branch: gh-pages — the branch GitHub Pages is configured to serve from.

    Do not add caching steps beyond what actions/setup-node@v4 provides via the cache: 'npm' option.
    Do not add a concurrency group — for this project, sequential deploys are acceptable.
    Do not pin actions to SHA hashes — use @v4 tags as specified in D-09.
  </action>

  <name>Task 2: Add public/.nojekyll to prevent Jekyll processing</name>
  <files>public/.nojekyll</files>

  <read_first>
    - vite.config.ts — confirm the includeAssets glob pattern; Vite also copies all public/ directory files to dist/ at build time regardless of includeAssets (the includeAssets glob controls the Workbox precache list, not the Vite copy behavior)
    - public/ directory listing (ls public/) — confirm .nojekyll does not already exist before creating it
  </read_first>

  <action>
    Check whether public/.nojekyll already exists using Bash: ls public/.nojekyll 2>/dev/null

    If it already exists: skip creation and proceed to verify.
    If it does not exist: create public/.nojekyll as an empty file using the Write tool (empty string content).

    This file serves one purpose: when Vite builds, it copies all files from public/ to dist/. The file dist/.nojekyll signals to GitHub Pages not to process the deployment with Jekyll. Without it, Jekyll strips files whose names start with underscore (e.g. _app.*.js from future bundler outputs) or interprets files incorrectly.

    Do not add any content to the file — it must be empty (zero bytes). GitHub Pages only checks for the file's existence.

    Do not add .nojekyll to the Workbox includeAssets glob — it is a deployment artifact, not a precached PWA asset, and it should not be served from the service worker cache.

    After creating the file, run npm run build and verify that dist/.nojekyll exists in the build output.
  </action>

  <verify>
    <automated>
      ls public/.nojekyll
      npm run build 2>&1 | tail -3
      ls dist/.nojekyll
    </automated>
  </verify>

  <acceptance_criteria>

    - npm run build exits with code 0
    - dist/.nojekyll exists after npm run build (Vite copies it automatically from public/)
    - npm run test exits with code 0
  </acceptance_criteria>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → npm registry | npm ci runs in the runner; supply chain attack via transitive deps could inject malicious code into the build |
| GitHub Actions runner → gh-pages branch | peaceiris/actions-gh-pages@v4 pushes to gh-pages; a compromised action could push malicious content |
| gh-pages branch → GitHub Pages CDN → Browser | Static file delivery; HTTPS prevents MITM |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-03-01 | Tampering | GitHub Actions workflow | high | mitigate | Workflow only triggers on push to main; branch protection rules on main (repo setting, not workflow config) enforce PR review before merge — outside scope of this plan but recommended |
| T-05-03-02 | Tampering | peaceiris/actions-gh-pages@v4 | medium | mitigate | @v4 tag pinned to a stable release by the peaceiris maintainers; SHA pinning is a future hardening option; npm run test gate ensures code quality before any deploy |
| T-05-03-03 | Tampering | Supply chain via npm ci | high | mitigate | npm ci uses package-lock.json for deterministic installs; lockfile integrity prevents version drift |
| T-05-03-04 | Elevation of Privilege | GITHUB_TOKEN write access | medium | mitigate | permissions: contents: write is scoped to the repository only; peaceiris/actions-gh-pages@v4 uses the token solely to push to gh-pages branch |
| T-05-SC | Tampering | npm/pip/cargo installs | low | accept | Plan 05-03 installs no new npm packages; all packages used (actions/checkout, actions/setup-node, peaceiris/actions-gh-pages) are GitHub Actions, not subject to npm package legitimacy gate |
