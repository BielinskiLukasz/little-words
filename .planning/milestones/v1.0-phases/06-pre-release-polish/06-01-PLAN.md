    In `src/db/db.ts`: append a `this.version(3).stores({...}).upgrade(tx => ...)` block inside the AppDB constructor, AFTER the existing `version(2)` block. The stores object is identical to v2 (no index changes on wordFormMeanings — compound key `[wordFormId+meaningId]` stays, per D-01). The upgrade callback:

    1. Reads all rows from `tx.table('wordFormMeanings')` via `.toArray()`
    2. For each pair, reads the parent Meaning via `tx.table('meanings').get(pair.meaningId)`
    3. If the meaning exists: calls `tx.table('wordFormMeanings').update(pair.id, { firstObservationDate: meaning.firstUseDate, lastUsedDate: meaning.lastUseDate, isActive: meaning.isActive })`
    4. If the meaning is not found (orphan pair, should not occur in practice): sets safe defaults: `firstObservationDate` and `lastUsedDate` to today's date (`new Date().toISOString().slice(0, 10)`), `isActive: false`

    Use async/await inside the upgrade callback. `tx.table(...)` returns an untyped Dexie Table — no TypeScript generics needed here.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01-01 | Tampering | updateMeaning / updateWordForm | medium | mitigate | Validate non-empty text before `db.update()` call; throw Error on empty string so caller can surface to user |
| T-06-01-02 | Tampering | Dexie v3 upgrade callback | medium | mitigate | Upgrade runs inside Dexie's built-in transaction; if any step throws, Dexie rolls back the entire upgrade atomically |
| T-06-01-03 | Information Disclosure | schema migration DB state | low | accept | Migration failure surfaces as Dexie blocked/failed event; no sensitive data is exposed; app fails to open cleanly |
