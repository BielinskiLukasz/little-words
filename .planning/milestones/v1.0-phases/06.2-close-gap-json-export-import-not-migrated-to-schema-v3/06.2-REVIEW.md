## Critical Issues

### CR-01: A backup with zero `childProfile` records passes validation and locks the user out of their own imported data

**File:** `src/features/settings/services/dataManagement.ts:79`, `src/features/settings/services/dataManagement.ts:193-208`
**Issue:** `validateBackupData` only checks `Array.isArray(d.childProfile)` (line 79) — an empty array is valid. `importData` then clears all four tables and `bulkAdd`s whatever was in the file, including zero `childProfile` rows (lines 200-207). `AuthGuard` (`src/router/index.tsx:23-35`) redirects to `/onboarding` whenever `db.childProfile.count() === 0`. So a backup file that is well-formed except for having `childProfile: []` will: (1) pass `validateBackupData`, (2) wipe any existing profile the user had, (3) successfully bulkAdd the (empty) profile set, (4) report `settings.importSuccess`, and then (5) bounce the user to onboarding with all their `wordForms`/`meanings`/`wordFormMeanings` still in IndexedDB but unreachable through the UI (which always gates on a profile existing). The user has no in-app way to discover that their data is still there — from their perspective the import silently destroyed everything.

This is reachable any time a user is handed (or hand-edits, or receives from a buggy future export path) a backup file with an empty `childProfile` array; nothing in `importData` guards against it today.

**Fix:**
```ts
function isValidChildProfile(item: unknown): boolean { /* unchanged */ }

// in validateBackupData, after the Array.isArray checks:
if (!Array.isArray(d.childProfile)) return false
if (d.childProfile.length !== 1) return false // exactly one profile — matches AuthGuard's single-profile assumption
```
(Or, at minimum, `d.childProfile.length < 1` if multiple profiles should still be tolerated — but zero must be rejected as `corrupt` rather than silently accepted.)

## Warnings

### WR-01: `escapeCSVCell` does not neutralize formula-injection prefixes (CSV/Excel injection)

**File:** `src/features/settings/services/dataManagement.ts:92-97`
**Issue:** `escapeCSVCell` only implements RFC 4180 quoting (commas, quotes, newlines). It does not defend against cells whose content starts with `=`, `+`, `-`, or `@`, which Excel/LibreOffice interpret as formulas (CWE-1236, "CSV Injection"). Since `meaning.text` and word forms are free-text fields a parent can type anything into, a value like `=HYPERLINK("http://evil","click")` or a DDE payload written into a meaning would be exported verbatim and could execute when the file is opened — and per the project's own core value proposition, this CSV is explicitly meant to be handed to a third party (a speech therapist/neurologist), not just reopened by the same user.
**Fix:**
```ts
function escapeCSVCell(value: string): string {
  // Neutralize formula-injection prefixes before RFC 4180 quoting
  if (/^[=+\-@]/.test(value)) {
    value = `'${value}`
  }
  if (value.includes(',') || value.includes('"') || value.includes('\n') || value.includes('\r')) {
    return '"' + value.replace(/"/g, '""') + '"'
  }
  return value
}
```

### WR-02: `isValidMeaning` doesn't validate `categories` values against the canonical `CATEGORIES` list

**File:** `src/features/settings/services/dataManagement.ts:50-60`
**Issue:** `isValidMeaning` checks `Array.isArray(m.categories)` but never verifies each element is one of the fixed `CATEGORIES` strings from `src/db/schema.ts`. A hand-edited or corrupted backup with `categories: ["Toys"]` (not a real category) will import successfully, then render as a raw, untranslated i18n key everywhere `t('category.Toys')` is used (Categories page, Doctor Report "top categories", etc.), and will never match any of the real category filters.
**Fix:**
```ts
import { CATEGORIES } from '@/db/schema'
// ...
function isValidMeaning(item: unknown): boolean {
  if (typeof item !== 'object' || item === null) return false
  const m = item as Record<string, unknown>
  return (
    typeof m.text === 'string' &&
    Array.isArray(m.categories) &&
    m.categories.every((c) => (CATEGORIES as readonly string[]).includes(c as string)) &&
    typeof m.isActive === 'boolean' &&
    typeof m.firstUseDate === 'string' &&
    typeof m.lastUseDate === 'string'
  )
}
```

### WR-03: No referential-integrity check between `wordFormMeanings` and the imported `wordForms`/`meanings` arrays

**File:** `src/features/settings/services/dataManagement.ts:62-88`
**Issue:** `isValidWordFormMeaning` checks types only; nothing verifies that a given row's `wordFormId`/`meaningId` actually corresponds to an entry in the same backup's `wordForms`/`meanings` arrays. A backup with dangling ids will import "successfully" and produce orphan pairs in the DB. `buildMeaningsCSV` happens to tolerate this defensively (`.find(...)?.form ?? ''`), but other UI surfaces that join across these tables (word-form/meaning detail pages, pairs list) were not verified here and this is exactly the kind of malformed-but-technically-typed data `validateBackupData` exists to catch.
**Fix:** After the per-array `.every(isValidX)` checks, add a referential pass, e.g.:
```ts
const wordFormIds = new Set(d.wordForms.map((wf: any) => wf.id))
const meaningIds = new Set(d.meanings.map((m: any) => m.id))
if (!d.wordFormMeanings.every((wfm: any) => wordFormIds.has(wfm.wordFormId) && meaningIds.has(wfm.meaningId))) return false
```

### WR-04: `wordForms` import path has no test coverage

**File:** `src/features/settings/services/dataManagement.test.ts:220-317`
**Issue:** The `importData` describe block has dedicated tests for `childProfile` (line 232), `meanings` (line 249), and `wordFormMeanings` (line 266), but none for `wordForms` — despite `buildBackupData`/`validateBackupData`/`importData` all handling it identically to the other three arrays. `06.2-CONTEXT.md` D-06 item 1 calls for a round-trip test of "valid v3 fixture data" restoring correctly, which implies all four entities, not three of four. If a future edit to `isValidWordForm` or the `bulkAdd` ordering breaks word-form restore, no test in this suite would catch it.
**Fix:** Add a test mirroring the existing `meanings` case:
```ts
it('imports wordForms records from a valid backup file', async () => {
  const { importData } = await import('./dataManagement')
  const backup: BackupData = {
    schemaVersion: 3,
    exportedAt: new Date().toISOString(),
    childProfile: [],
    wordForms: [{ id: 1, form: 'mama', createdAt: '2024-01-01' }],
    meanings: [],
    wordFormMeanings: [],
  }
  const file = new File([JSON.stringify(backup)], 'backup.json', { type: 'application/json' })
  await importData(file)
  const forms = await testDb.wordForms.toArray()
  expect(forms).toHaveLength(1)
  expect(forms[0].form).toBe('mama')
})
```

### WR-05: The destructive "replace all data" contract of `importData` is untested

**File:** `src/features/settings/services/dataManagement.test.ts:220-230`
**Issue:** `importConfirmDescription` promises the user "This will permanently delete all current data" (`src/i18n/locales/en/common.json:56`), and `importData` implements this via `clear()` calls before each `bulkAdd` (`dataManagement.ts:200-207`). No test in this suite seeds pre-existing rows in `testDb` before calling `importData` and then asserts they are gone afterward — every existing test starts from an empty DB, so the "replace" half of "replace all data" is never actually exercised. This is the single most consequential (and irreversible) behavior in this file and it has no regression coverage.
**Fix:**
```ts
it('replaces pre-existing data instead of appending to it', async () => {
  const { importData } = await import('./dataManagement')
  await testDb.meanings.add({ text: 'stale', categories: ['Other'], isActive: true, firstUseDate: '2020-01-01', lastUseDate: '2020-01-01' })
  const backup: BackupData = {
    schemaVersion: 3,
    exportedAt: new Date().toISOString(),
    childProfile: [],
    wordForms: [],
    meanings: [{ id: 99, text: 'fresh', categories: ['Other'], isActive: true, firstUseDate: '2025-01-01', lastUseDate: '2025-01-01' }],
    wordFormMeanings: [],
  }
  const file = new File([JSON.stringify(backup)], 'backup.json', { type: 'application/json' })
  await importData(file)
  const meanings = await testDb.meanings.toArray()
  expect(meanings).toHaveLength(1)
  expect(meanings[0].text).toBe('fresh')
})
```

## Info

### IN-01: Non-numeric `schemaVersion` silently downgrades the error message

**File:** `src/features/settings/services/dataManagement.ts:183-191`
**Issue:** The specific `wrong-schema-version` path only fires when `typeof schemaVersion === 'number'`. A backup with `schemaVersion: "3"` (string) skips this branch, falls through to `validateBackupData` (`d.schemaVersion !== BACKUP_SCHEMA_VERSION` is `true` for `"3" !== 3`), and the user sees the generic "doesn't appear to be a backup" message instead of the more accurate version-mismatch one. Low likelihood in practice (real exports always emit a number), but worth a one-line comment or a `Number(schemaVersion) === BACKUP_SCHEMA_VERSION` normalization if it's ever seen in the wild.
**Fix:** Optional — document the assumption or loosen the type check to `Number(...)`.

### IN-02: `dataManagement.ts` bypasses the project's DB-service-layer convention

**File:** `src/features/settings/services/dataManagement.ts:126-132, 150-155, 199-208`
**Issue:** `CLAUDE.md` states: "Database access: always go through the service layer in `src/db/services/`; never call Dexie tables directly from components or pages," and services should be named `*.service.ts` under `src/db/services/`. `dataManagement.ts` lives under `src/features/settings/services/` (not `src/db/services/`), is not suffixed `.service.ts`, and calls `db.childProfile.toArray()`, `db.wordForms.toArray()`, `db.transaction(...)`, etc. directly. This predates the current phase, but the file is fully in review scope; flagging for awareness/backlog rather than as a phase-blocking issue.
**Fix:** Consider extracting the raw Dexie reads/writes (`exportData`'s `Promise.all([...toArray()])` and `importData`'s `db.transaction(...)` block) into a new `src/db/services/backup.service.ts`, leaving `dataManagement.ts` with only the pure functions (`buildBackupData`, `validateBackupData`, `buildMeaningsCSV`) plus thin wrappers that call the service.

### IN-03: Repeated type-guard boilerplate across the four `isValidX` functions

**File:** `src/features/settings/services/dataManagement.ts:33-72`
**Issue:** `isValidChildProfile`, `isValidWordForm`, `isValidMeaning`, and `isValidWordFormMeaning` all start with the identical `if (typeof item !== 'object' || item === null) return false` guard. Minor duplication; a shared `asRecord(item): Record<string, unknown> | null` helper would remove four copies of the same check and make it easier to extend all four consistently (e.g., when adding the WR-02/WR-03 checks above).
**Fix:**
```ts
function asRecord(item: unknown): Record<string, unknown> | null {
  return typeof item === 'object' && item !== null ? (item as Record<string, unknown>) : null
}
```
