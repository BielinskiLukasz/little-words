# Phase 06.2: Close gap: JSON export/import not migrated to schema v3 - Context

**Gathered:** 2026-09-17
**Status:** Ready for planning

<domain>
## Phase Boundary

Settings JSON export/import (`src/features/settings/services/dataManagement.ts`) must correctly reflect the Dexie v3 schema. Today `buildBackupData` hardcodes `schemaVersion: 2`, `isValidWordFormMeaning` doesn't require the v3 per-pair fields (`firstObservationDate`, `lastUsedDate`, `isActive`), and `importData` rejects anything other than exactly `2` — meaning the JSON backup/restore feature was never updated when Phase 6 moved rollup fields onto `WordFormMeaning` (milestone v1.0 audit, blocker 2: DATA-02/PREREL-03).

Out of scope: CSV export (`buildMeaningsCSV`/`exportMeaningsCSV`) — flagged separately in the audit as tech debt, not this phase's goal; the meaning-rollup aggregation gap (already closed in Phase 06.1); any new data-management capability (e.g. selective/partial export, cloud backup).

</domain>

<decisions>
## Implementation Decisions

### Schema Version Bump

- **D-01:** Extract a single named constant (e.g. `BACKUP_SCHEMA_VERSION = 3`) in `dataManagement.ts`, used by both `buildBackupData` (sets `schemaVersion`) and `importData`'s version check (`!== BACKUP_SCHEMA_VERSION`). This directly targets the root cause the audit identified — the literal `2` was hardcoded in two places and never updated when Dexie moved to v3 — so the next schema bump only requires changing one line. It does not auto-sync with `db.verno`; that coupling is explicitly not being introduced here.
- **D-02:** Import requires `schemaVersion === BACKUP_SCHEMA_VERSION` exactly (not `>=`). A future v4 bump needs its own explicit compatibility decision — accepting `>= 3` today would let a genuinely different v4 file pass validators that only know v3 field shapes, risking exactly the silent-corruption class of bug this phase fixes. — **Reversibility:** reversible (a future phase can loosen this if a real forward-compat need arises).

### Legacy v2 Backup Handling

- **D-03:** A backup with `schemaVersion: 2` (or any value other than 3) is rejected outright via the existing `wrong-schema-version` error path — no auto-migration/backfill of per-pair fields from the parent Meaning. Confirmed with the user: no real v2 backups exist yet (app hasn't shipped v1.0; any prior exports were dev/test data), so rejection carries no real migration cost. — **Reversibility:** reversible (a migration path could be added later if a real v2 backup surfaces).
- **D-04:** Fix the existing `importErrorDescriptionVersion` i18n string (both `en` and `pl`) — it currently reads "This backup is from a **newer** version of the app" (`src/i18n/locales/en/common.json:60`, `pl/common.json:62`), which is factually wrong for the v2→v3 case (the file is older, not newer). Reword to version-neutral phrasing, e.g. "This backup was made with a different version of the app and cannot be imported" (and the Polish equivalent). This is a real user-facing bug surfaced during discussion, not scope creep — it's the exact error path this phase's version check produces.

### Per-Pair Field Validation

- **D-05:** `isValidWordFormMeaning` must require `firstObservationDate: string`, `lastUsedDate: string`, and `isActive: boolean` to be present with correct types, rejecting the import (`corrupt` error) if any are missing or mistyped — same strict-typing style already used by `isValidChildProfile`/`isValidMeaning` in the same file. No loose/presence-only checking.

### Test Coverage

- **D-06:** Update `dataManagement.test.ts` to cover:
  1. Round-trip: `buildBackupData` emits `schemaVersion: 3`; export → import of valid v3 fixture data (including populated per-pair fields) restores correctly.
  2. Rejection: a v2-shaped fixture (missing per-pair fields, `schemaVersion: 2`) is rejected via `wrong-schema-version`.
  3. Rejection: a v3-shaped fixture missing one required per-pair field (e.g. `isActive`) is rejected via `corrupt`.

### Claude's Discretion
- Exact placement/naming of the `BACKUP_SCHEMA_VERSION` constant (top of `dataManagement.ts` is the obvious choice, alongside the `BackupData` interface).
- Exact wording of the reworded `importErrorDescriptionVersion` strings in both locales, as long as they're version-direction-neutral.

</decisions>

## Existing Code Insights

### Reusable Assets
- `isValidChildProfile`/`isValidMeaning` in `dataManagement.ts` — exact strict-typing validator style to mirror for the `isValidWordFormMeaning` fix (D-05)
- Existing `wrong-schema-version` / `corrupt` error-throwing pattern in `importData` — reuse as-is, only the version number and validator logic change

### Established Patterns
- `dataManagement.ts` functions are pure where possible (`buildBackupData`, `validateBackupData`, `buildMeaningsCSV` take arrays, no DB access) — keep the fix consistent with this, no new DB calls needed
- Version check happens before full structural validation in `importData` (lines 174-183) specifically to produce a more specific error message — preserve this ordering

### Integration Points
- `DataSection.tsx:52-58` — catches the thrown error and maps `message.includes('wrong-schema-version')` to the version-error i18n string; no changes needed here since the error contract (`Error('wrong-schema-version')` / `Error('corrupt')`) stays the same
- `dataManagement.test.ts` — existing fixtures presumably use `schemaVersion: 2` and lack per-pair fields; must be updated to v3 shape as part of this fix, not left stale

### Critical Notes
- This is the second of two milestone v1.0 audit blockers (the first, meaning-rollup aggregation, was closed in Phase 06.1) — both stem from the same root cause: Phase 6's schema v3 migration wasn't threaded through code written in earlier phases
- CSV export (`buildMeaningsCSV`) has its own schema-divergence tech debt noted in the audit but is explicitly NOT part of this phase's goal (ROADMAP §Phase 06.2 goal only mentions JSON export/import)
