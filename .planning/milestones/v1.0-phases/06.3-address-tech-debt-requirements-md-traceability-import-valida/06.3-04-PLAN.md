<objective>
Close the single remaining gap from `06.3-VERIFICATION.md` (code review finding WR-01): `importData`'s specific-error pre-check for `childProfile` only fires when `childProfile` is present **and** is an array **and** has the wrong length. When `childProfile` is missing entirely, `null`, or not an array at all, execution falls through to the generic `corrupt` error path — even though the shipped i18n message (`settings.importErrorDescriptionMissingProfile`, "This backup file has no child profile data...") explicitly claims to cover exactly this case.

Purpose: A parent restoring a hand-edited or partially-corrupted backup file that is missing the `childProfile` key altogether (a very plausible corruption shape) must see the specific "no child profile data" message this phase already shipped for that purpose, not the generic "this doesn't look like a Little Words backup" message. This extends D-02's distinct-error guarantee (06.3-01) to cover every invalid shape of `childProfile`, not only the wrong-length-array shape.

Output: `importData`'s `childProfile` pre-check is widened so any invalid shape — missing key, `null`, non-array, or wrong-length array — throws the same `Error('invalid-child-profile-count')` before `db.transaction` runs. `validateBackupData` is verified (via new regression tests, not a code change — it is already correct) to independently return `false` for the same missing/null/non-array shapes.
