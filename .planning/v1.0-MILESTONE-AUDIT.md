# Milestone v1.0 Audit — Little Words

**Audited:** 2026-09-16
**Scope:** Phases 1–6 (Foundation → Onboarding & Data Entry → Browse Views → Doctor Report & Data Management → PWA Polish → Pre-release Polish)
**Status:** ⚠ Gaps Found

## Summary

All 6 phases report `passed` (or `passed` after UAT superseded an initial `human_needed` verdict) at the phase-verification level, and every phase's own UAT suite is at 100% pass with 0 skips (after post-phase quick-fix tasks closed 3 deferred items from Phase 6's UAT). Individually, each phase is solid.

The milestone-level integration check found **two blockers that only appear when phases are exercised together**, both stemming from the Phase 6 schema v3 migration (moving `isActive`/`firstUseDate`/`lastUseDate` from `Meaning` to a per-pair rollup on `WordFormMeaning`) not being fully threaded through code written in earlier phases:

1. **Reusing an existing meaning via the add-entry autocomplete never refreshes that meaning's rollup fields**, so the Active Meanings count on the Dashboard (the app's headline number) and the Doctor Report can go stale.
2. **JSON export/import (Settings → Data) was never updated for the v3 schema** — the exported `schemaVersion` is hardcoded to `2`, and import validation doesn't require the new per-pair fields, creating a silent-corruption risk on restore.

Neither blocker was caught by phase-level verification because each phase's UAT only exercises paths introduced *within* that phase; both defects live at the seam between an earlier phase's code and Phase 6's schema change.

## Broken Flows

- **Add word entry (reuse existing meaning) → Dashboard/Browse/Report:** breaks at the rollup-recomputation step. The link itself succeeds and the UI shows no error, but the previously-inactive meaning's status doesn't refresh until an unrelated edit happens to trigger `aggregateMeaningFromPairs`.
- **Settings → Export JSON → Import JSON (round trip on current schema):** breaks at schema-version/field-validation mismatch. A backup taken today is mislabeled as `schemaVersion: 2` and, more importantly, a malformed or hand-edited file missing the new pair-level date fields would be silently accepted and written to IndexedDB with `undefined` dates, corrupting subsequent rollup computations (`NaN`/`Invalid Date`).

## Tech Debt (Non-Blocking)

- Two independent CSV export code paths (Settings DataSection vs. PairsPage) with different granularity — maintenance risk, not a functional bug.
- `unlinkMeaning()` is dead code with no live caller and no re-aggregation call — low risk since nothing invokes it, but should be removed or clearly marked deprecated-only-for-tests.
- Phase 2 UAT test 13 (DB error surfacing) was skipped as "can't test" — minor, non-blocking.
- iPadOS 13+ install-prompt detection gap (WR-05) — deferred, non-blocking, cosmetic.

## Verdict

**gaps_found.** Both blockers are narrow, well-localized fixes:

1. Call `aggregateMeaningFromPairs(meaningId)` after linking in the dedup branch of `addWordEntry` (or move the call inside `linkMeaningToWordForm` itself, matching the pattern already used by `updatePairFields`).
2. Bump `buildBackupData`'s `schemaVersion` to `3`, extend `isValidWordFormMeaning` to require `firstObservationDate`/`lastUsedDate`/`isActive`, and decide on a migration/rejection strategy for existing users' v2 backup files.

Given the app's core value proposition ("a parent can walk into a specialist consultation and present objective, structured observations"), both defects directly threaten data trustworthiness — the Active Meanings count and Doctor Report are the app's primary outputs, and JSON export/import is the only data-portability path this app offers. Recommend closing both before calling v1.0 done.
